# RAG Implementation Plan

## Overview

This document outlines the plan for building a local RAG (Retrieval Augmented Generation) system that allows LLMs to access markdown notes efficiently. The system indexes notes from a private GitHub repository into a local vector database and enables natural language querying with responses generated by a self-hosted Ollama instance.

## Goals

- **Local-first**: All processing (indexing, embeddings, LLM inference) happens locally
- **No external providers**: Avoid cloud APIs; use open-source libraries and local models
- **Efficient retrieval**: Chunk-based indexing with semantic search for fast information access
- **Simple re-indexing**: CLI command to trigger daily re-indexing process
- **HTTP API**: Expose `/query` endpoint for easy integrations (e.g., MCP, web apps)

## Workflow

### Indexing Workflow (`./rag index`)

```
1. CLI Trigger (click)
   ↓
2. Clone/Pull Notes Repo (GitPython)
   - Read NOTES_REPO_URL and NOTES_TOKEN from environment
   - Clone/pull to NOTES_CACHE_DIR (./notes-cache/)
   - Handle auth via token in URL: https://ghp_xx@github.com/user/repo.git
   ↓
3. Discover Markdown Files
   - Recursively walk ./notes-cache/ for all .md files
   - Ignore hidden files/folders
   ↓
4. Parse & Chunk
   - Use LlamaIndex MarkdownReader
   - Chunk by character size (1000 chars, 200 overlap)
   - Preserve markdown formatting
   ↓
5. Generate Embeddings
   - Use sentence-transformers with all-MiniLM-L6-v2
   - Generate 768-dimensional vectors
   ↓
6. Store in ChromaDB
   - Store embeddings with metadata: source_file, chunk_index
   - Print summary: N files, M chunks
```

### Query Workflow (`./rag query "question"`)

```
1. CLI Trigger (click)
   ↓
2. Query Embedding Generation
   - Use same model as indexing (all-MiniLM-L6-v2)
   ↓
3. Similarity Search
   - Query ChromaDB for top-k similar chunks (default k=5)
   - Retrieve chunk text + source file metadata
   ↓
4. Context Assembly
   - Combine retrieved chunks into context string
   - Format with separators
   ↓
5. LLM Response Generation via Ollama
   - Prompt template with context + question
   - Call ${OLLAMA_HOST}/api/generate
   - Model: ${OLLAMA_MODEL} (default: mistral)
   - Instruction: Include citations in format [source: path/to/file.md]
   ↓
6. Output
   - Print generated response with inline citations
   - Exit with status 0
```

## Chunking Strategy

- **Method**: Character-based recursive character text splitter
- **Chunk size**: 1000 characters (configurable via CHUNK_SIZE)
- **Overlap**: 200 characters (configurable via CHUNK_OVERLAP)
- **Parser**: `MarkdownReader` with `keep_table_as_text=True`
- **Metadata**: Each chunk includes source_file (relative path)

**Rationale**: Simple character-based chunking provides good balance between context preservation and computational efficiency. Can be improved later with header-aware hierarchical chunking if needed.

## Prompt Template

The Ollama prompt for response generation:

```
You are a helpful assistant that answers questions using provided context.

Context from user notes:
---
{context}
---

Question: {question}

Please provide a concise answer and include source citations in the format [source: path/to/file.md] wherever you use information from the context. If you cannot find the answer in the context, state that clearly.

Answer:
```

**Citation format**: Inline citations like "Redis is used for caching [source: notes/backend.md]"

## Environment Variables

| Variable | Description | Required | Default |
|----------|-------------|----------|---------|
| `OLLAMA_HOST` | Base URL of Ollama API (including port) | Yes | - |
| `OLLAMA_MODEL` | Model name for generation (e.g., mistral, llama2) | Yes | - |
| `NOTES_REPO_URL` | GitHub repo URL with token (https://ghp_xx@...) | Yes | - |
| `NOTES_CACHE_DIR` | Local cache directory for cloned repo | No | `./notes-cache` |
| `EMBEDDING_MODEL` | Sentence-transformers model name | No | `all-MiniLM-L6-v2` |
| `TOP_K` | Number of chunks to retrieve per query | No | `5` |
| `CHUNK_SIZE` | Maximum chunk size in characters | No | `1000` |
| `CHUNK_OVERLAP` | Overlap between chunks in characters | No | `200` |

## Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| **Framework** | LlamaIndex | Better native support for file-based RAG, simpler API |
| **Vector DB** | ChromaDB | Local-first, Python-native, minimal setup overhead |
| **Embedding Model** | all-MiniLM-L6-v2 | Fast, lightweight (~90MB), good quality for retrieval |
| **Chunking** | Simple character-based | Start simple, can improve with header-aware later |
| **LLM** | Ollama (local) | Self-hosted, flexible, supports citation generation |
| **Git Auth** | Token in URL | Simpler than credential helper setup, reliable |
| **Citations** | Inline format [source: path] | Provides transparency, helps verify accuracy |

## Future Improvements

1. **Header-aware chunking**: Preserve document hierarchy (Chapter > Section > Content)
2. **Hybrid search**: Combine keyword (BM25) and semantic search
3. **Query rewriting**: Improve query embeddings for better retrieval
4. **Incremental indexing**: Only index new/modified files, not full rebuild
5. **Citation ranking**: Prioritize chunks from more recent/authoritative sources
6. **Multi-model support**: Swap embedding models or LLMs without code changes

## Security Considerations

- **NOTES_TOKEN** should never be committed; use `.env` or shell export
- **notes-cache/** directory is added to `.gitignore` to prevent accidental commits
- Token format: `https://ghp_xx@github.com/user/repo.git` (GitHub Personal Access Token)
- Consider rotating tokens periodically; Ollama API should be on localhost or trusted network

## Testing Strategy

- **Unit tests**: Isolate config loading, storage operations, prompt generation
- **Integration tests**: Test with sample markdown files and mock Ollama
- **Manual testing**: Verify indexing workflow and query responses end-to-end
- **Validation**: Check citation formats, embedding quality, response relevance

## Performance Considerations

- **Embedding model**: `all-MiniLM-L6-v2` is fast (~1ms/chunk) and memory-efficient
- **ChromaDB**: In-memory by default; can persist to disk for larger deployments
- **Ollama**: Local inference latency depends on model size and hardware (typically 5-50ms/token)
- **Chunking**: Parallel file processing can be added if indexing becomes slow
